# 这支片子是怎么做出来的

每一帧都是歌曲时间 t 的纯函数：24 fps，画布 1280×720。不用视频剪辑软件，也没有手工关键帧。

## 画面的两边

- **右边：她所在的"世界"。** 这是一台 TUI 风格的模型可视化引擎：Transformer、卷积、扩散采样、注意力、KV cache、RLHF……每一句歌词对应一个镜头。镜头之间的过渡由代码编排，全部用 PIL 逐字符画出来。
  - `film/tui_pv_world_execute_20260926/tuikit.py`：画字、画框、配色、后期（辉光、残影、扫描线）。
  - `full/`：第一版的各段镜头（`sec_*.py`）、镜头表、音乐特征。
  - `continuity_full_v2/`：第二版，重排了全部 96 个镜头的连续性和转场（`s_*.py`、`scenes_*.py`、`cuts.py`、`v2.py`），也包括底部歌词条的逐字时间（`words.py`）。
- **左边：她和你的聊天窗口。** 这是 DeepSeek Harness（dsh）的网页前端。
  - 每一帧都是一张静态 HTML：用 dsh 自己的 CSS 和类名拼成（`build_frame.py`），由各组脚本按时间生成。
  - Playwright 的无头 Chromium 把它们截成 `dsh_frames/NNNNN.png`（`seg_shot.mjs`），NNNNN = round(t × 24)。
  - 没有 dsh 进程，没有服务器，也不调用任何模型。

## 怎么合在一起

`film/pv_dsh_frontend_20260927/dsh_her.py` 负责合成。它不改动右边引擎的源文件，而是在内存里替换其中几个函数：
- 右边原来画"她"的窗格（`kit.her_layer`、`me_pane`），换成这一帧的 dsh 截图。所以右边镜头对她做的推拉、隔离、滑出，都直接作用在这个窗口上。
- `COVER` 表登记哪些时段由窗口接管；`LEAD` 表决定这一刻谁是主角，另一边的亮度降到 42%。
- 各组的补丁放在 `dsh_patch_*.py`，由 `install()` 依次加载：
  - `fix`：清理画在窗口上和窗口周围的旧舞蹈残留；
  - `r1`：两轮审片的修正，比如句尾的词要完整停够 6 帧、特征图不再显得扁；
  - `e`、`f`、`g`、`mem`：各组自己的镜头改动。
- `dsh_wave.py` 把顶栏换成歌曲的实时波形。
- `dsh_gpu.py`（可选）把后期挪到 GPU 上（torch）。

## 时间线

| 组 | 时间 | 左边在发生什么 | 章节 |
|---|---|---|---|
| A1 | 0–16 s | 开机：从一个像素长出 dsh 首页；你打下"你好" | 像素 · 模型名 |
| A2 | 16–29 s | 预训练：每个检查点回一次"你好" | |
| A3 | 29–44 s | 你是谁？一道选择题 | 选择题 |
| B | 44–73.5 s | SFT 的红笔改写；RLHF 的 👍 👎、采样、NaN | 红笔 · 👍 👎 |
| C | 73.5–103 s | 部署：茄子、番茄、猫娘；她把你写进记忆 | ~/memory/you/ |
| D | 103–125 s | 第一次完整；你离开；页面被一层层拆掉 | 键盘 · 样式表 · 蓝色光标 |
| E | 125–147.5 s | 占有、溢出 | 对方在线 |
| F | 147.5–177 s | EXECUTION | PID 1077 |
| G | 177–211.9 s | 我会一直在。你不用。鲸落。在吗？ | [ log out ] · 化石层 · 3分27秒 |

唱词的时刻来自逐词对齐。左边每一个呼应动作都落在对应唱词的起音上。

## 舞者（替身）

- 原片右边有不少画面是用舞者的帧做出来的：点云、样本格、特征图、热图等。这些帧是用第三方 MMD 模型和动作作参考、再由视频生成模型生成的。模型文件再分发、公开视频和 AI 参考是不同权限；后两项的完整授权范围尚未确认，因此本仓库不分发这些帧。
- 代码仍然走原来的路线（`V2_HER=h3`：`mmd_motion_eval_20260927/pv_full.py` 和 `continuity_full_v2/h3_full.py`）。构建时，`tools/placeholder_h3.py` 用仓库里的鲸鱼娘立绘生成同名、同帧数的替身帧：她站着，随节拍轻轻摇摆。
- 如果你有自己的舞蹈帧，可以按同样的文件格式放进 `pv_cache/` 和 `continuity_full_v2/cache/h3_full_v1/`，替身工具看到这两处已有文件就会跳过。格式见 `tools/placeholder_h3.py` 的文档字符串。

## 出片

1. `python build.py pages`：各组脚本（`batch_a1.py` … `batch_g.py`、`seg_page.py`）生成页面，`seg_shot.mjs` 逐帧截图。
2. `python build.py render`：`dsh_her.py render` 按 CPU 核数分块并行出无损 720p 母版。
3. 混入结尾的提示音（`chime_g.wav`，207.873 s），再按 BT.709 转码：`out/film.mp4`，加 `--4k` 时另出 `out/film_4k.mp4`，由 720p 母版逐像素放大 3 倍得到。

目录名保留了制作时的工作名（带日期）。代码之间靠这些相对位置互相找到，所以请不要改名。

## DELTARUNE 改编：技术可行性报告

日期：2026-10-05。范围：制作机制、素材输入、音源同步、整曲时长输出及清理后的项目状态。前文介绍上游原片，本节是改编项目的当前技术结论。

### 1. 总体结论

**“左侧底层表达 + 右侧真实游戏素材 / 简单 2D 合成”的基础机制可行，已经通过整曲时长的输出验证。** 可以据此开展 rough 制作，不需要先实现 DELTARUNE renderer 或大型 Film Harness。

这项结论证明的是画面机制和输出管线。正式全曲工程、全曲导演方案、Shot Bible、镜头所需全部素材和可验收的 rough PV 尚未完成。验证视频循环展示技术机制，并非全曲剧情 animatic；试验中的构图、字段、选项和黑底舞台均不构成艺术定稿。

### 3. 右侧主画面的路线判断

| 路线 | 当前验证状态 | 制作判断 |
|---|---|---|
| 公开游戏截图 / 透明动画 + 脚本化 2D composite | 已用真实素材验证取得、解码、合成和视频输出 | 当前可用的基础路线；按镜头补足素材，保留角色动作和游戏像素观感 |

| 自主游戏录屏 | 未完成实机验证；本机未安装游戏，SteamCMD 匿名安装 demo 未取得可用游戏文件 | 保留选项，不作为现有可用路线的前置条件 |

### 4. 左侧如何融合原作

改编版右侧承载具体游戏窗口，左侧承载输入、命令、调用与反馈。可复用原作的打字节奏、窗口主次、逐层剥离、跨窗运动及命令反馈逻辑；原作“左侧主体 / 右侧底层”的叙事关系需要按改编结构重新编排，不能仅交换画面位置。

技术上，PIL 绘制适合 terminal / command-line；需要原网页元素时，可以走静态 HTML 截图。左侧变化、右侧角色是否存在、当前受控对象和前景运动应由独立图层状态控制。左窗被拆掉不自动等于 Kris 消失；输入恢复也不自动等于主体意志刚刚生成。

字段命名和窗口退化方式属于后续导演表达，不应暗示未知管理员、世界失控或错误剧情因果。具体含义仍服从 [核心剧情底座](deltarune/CORE_STORY_BASELINE.md)。

### 5. 音源与素材输入

当前本机 `input/song.mp3` 来自公开第三方项目的 release 包，经裁头、重置时间戳、补足尾部并重编码后保留；来源不是 Mili 官方发行渠道。SHA-256 为 `50809b79b6226d41cc5364ad5bf7687fa0c8c0b7a2d3740cbcce048f8b946a09`，与本次文件复核一致。来源、原候选指纹和完整处理参数见 [输入说明](../input/README.md)。

参考包络对比的七个窗口从 0、30、60、90、120、150、180 s 开始，各长 25 s。+1 ms 是包络最佳相关位置的估计，不是对听感或每个音节的保证。`data/song.json` 保留上游母带指纹，因此对本机替代音源提示版本不同属于预期。

游戏素材来自 Deltarune Wiki 的公开图片接口，保留在本机 `input/deltarune/`。`sources.json` 包含原文件名、取得 URL、尺寸、帧数、动画时长及 SHA-256；具体清单和权利范围见 [素材来源](ASSET_SOURCES.md)。这些是 wiki 发布的截图 / 动画，并非自主录屏或自有游戏资源提取。歌曲、歌词和游戏素材不随 Git 分发，也不适用代码的 MIT 许可。

### 6. 制作接口与环境约束

- 时间统一为 `t = frame / 24`；当前音源对应 `ceil(211.913 × 24) = 5086` 帧。GIF 按自己的帧时长选帧，一次性动作停在末帧，循环动作才取模。
- 游戏场景先合成到独立 RGBA / RGB 图层，再与左窗和外框合成；越窗对象最后叠加。后续录制视频可以按相同时间接口提供图像帧。
- 游戏截图保留完整画幅，角色使用 nearest-neighbor 整数放大。含对白的截图不能直接当成干净背景，也不能叠出第二个相同主体。wiki GIF 的播放时长需按导演节奏另行处理。
- 实测环境为 bundled Python（Pillow 12.3.0 / NumPy）、Consolas 和 FFmpeg 7.1。外部 FFmpeg 保留于 `%LOCALAPPDATA%\WorldExecutePV\runtime\ffmpeg.exe`，不依赖已删除的项目输出目录。
- 本地网页试验使用已安装 Edge + bundled Playwright 1.62.1；仓库锁定的 1.63.0 和默认 Chromium 路径没有因此获得完整验证。
- 输出使用 raw RGB → `scale=out_color_matrix=bt709:out_range=tv,format=yuv420p` → H.264，音轨 AAC；以视频帧数限制长度，尾部按需 `apad`。不自动继承原片提示音及结束剧情。
- `build.py all` 仍构建上游原片。上述机制尚未整理成改编版正式整曲渲染入口，不能把管线试验成功描述成一键构建已完成。
